1. ARQUITECTURA ACTUAL DEL PROYECTO
================================================================================

Stack
-----
  - Monorepo npm workspaces: frontend + backend (@cg/backend)
  - Frontend: Next.js 16, React 19, Tailwind 3
  - Backend: Lógica en @cg/backend, expuesta vía API routes de Next.js
  - Base de datos: Supabase PostgreSQL (o memoria local solo para desarrollo)
  - Tiempo real: Supabase Realtime + polling cada 10 segundos como respaldo
  - Identidad: sesión invitada por sala en cookie HttpOnly; el servidor valida el token
  - Deploy previsto: Vercel (frontend) + Supabase (DB + Realtime)

Flujo de una partida
--------------------
  1. Lobby
     El usuario introduce su nombre.
     POST /api/rooms          → crea sala
     POST /api/rooms/[code]/join → unirse a sala
     Redirección a /room/[code]

  2. Host inicia juego
     POST /api/rooms/[code]/game-type → elige blackjack o poker
     POST /api/rooms/[code]/start     → status = "playing", game_state inicial

  3. Gameplay
     POST /api/rooms/[code]/action → valida acción, muta estado, guarda en DB
     GET  /api/rooms/[code] → estado personalizado según cookie (oculta cartas rivales)

  4. Sincronización entre clientes
     Hook useRoom() en el navegador:
       - Suscripción Realtime al canal room:{code}
       - Escucha cambios en tablas rooms y room_players
       - Al detectar cambio → refetch vía REST
       - Polling cada 10000 ms siempre activo (respaldo)
       - Heartbeat cada 20000 ms para presencia y reconexión

Diagrama simplificado
---------------------
  Navegador
      |
      | REST (POST/GET /api/rooms/*)
      v
  Next.js API Routes
      |
      v
  room-service.ts  -->  motores blackjack / poker
      |
      v
  store.ts  -->  Supabase PostgreSQL  (producción)
              -->  memoria global      (solo dev local)

  Navegador
      |
      | useRoom() + Supabase Realtime
      v
  postgres_changes en rooms / room_players  -->  refetch estado

5. CONFIGURACIÓN PASO A PASO EN SUPABASE
================================================================================

Paso 1 — Crear proyecto
-----------------------
  1. Ir a https://supabase.com
  2. New project
  3. Elegir nombre, contraseña de base de datos y región cercana a usuarios
  4. Esperar a que el proyecto termine de crearse (~2 minutos)

Paso 2 — Ejecutar migración SQL
-------------------------------
  1. Dashboard Supabase → SQL Editor → New query
  2. Ejecutar en orden todos los archivos de:
       backend/supabase/migrations/001...005
  3. Pulsar Run tras pegar el contenido de cada archivo

  Esto crea:
    - Tabla rooms (salas, game_state JSONB, status lobby/playing/finished)
    - Tabla room_players (jugadores, chips, is_connected)
    - Índices en code y room_id
    - Trigger updated_at en rooms
    - Realtime en rooms y room_players
    - RLS con políticas rooms_read y players_read (solo SELECT)
    - Sesiones privadas, presencia y guardado transaccional

  NOTA: Si falla "ALTER PUBLICATION supabase_realtime ADD TABLE...",
  puede que las tablas ya estén en la publicación. En ese caso:
    Database → Replication → activar manualmente rooms y room_players.

Paso 3 — Verificar Realtime
---------------------------
  1. Database → Replication (o Publications)
  2. Confirmar que rooms y room_players están en supabase_realtime

Paso 4 — Copiar claves API
--------------------------
  Project Settings → API

  Guardar estos tres valores:

    NEXT_PUBLIC_SUPABASE_URL      → Project URL
    NEXT_PUBLIC_SUPABASE_ANON_KEY → anon public key
    SUPABASE_SERVICE_ROLE_KEY     → service_role secret key

  IMPORTANTE:
    - SERVICE_ROLE_KEY solo en servidor (Vercel env vars, .env.local)
    - NUNCA subir SERVICE_ROLE_KEY a GitHub ni usarla en código del browser
    - ANON_KEY sí puede ir al cliente (prefijo NEXT_PUBLIC_)

Paso 5 — Probar en local (recomendado antes de Vercel)
--------------------------------------------------------
  1. Copiar frontend/.env.example → frontend/.env.local
  2. Pegar las 3 variables con los valores de Supabase
  3. En la raíz del repo:
       npm install
       npm run dev
  4. Abrir http://localhost:3000
  5. Crear sala, abrir misma sala en otra pestaña/navegador
  6. Verificar sincronización de estado
  7. En Supabase → Table Editor → rooms: deben aparecer filas al crear salas

Paso 6 — Qué NO hace falta configurar ahora
---------------------------------------------
  - Supabase Auth (el juego usa tokens invitados seguros por sala)
  - Edge Functions (la lógica está en API routes de Next.js)
  - Storage
  - Docker

6. CONFIGURACIÓN PASO A PASO EN VERCEL
================================================================================

Paso 1 — Conectar repositorio
-----------------------------
  1. Ir a https://vercel.com
  2. Add New Project
  3. Importar repositorio GitHub: CG-PokerRepo

Paso 2 — Configuración del monorepo (CRÍTICO)
---------------------------------------------
  La app depende del workspace @cg/backend. Si Vercel solo hace npm install
  dentro de frontend/, el build FALLARÁ con "Cannot find module '@cg/backend'".

  OPCIÓN A — Recomendada (raíz del repositorio)
  ----------------------------------------------
    Root Directory:     .  (raíz del repo, no solo frontend)
    Framework Preset:   Next.js
    Install Command:    npm install
    Build Command:      npm run build
    (Output: Vercel detecta frontend/.next según configuración)

  OPCIÓN B — Root Directory = frontend
  --------------------------------------
    Root Directory:     frontend
    Install Command:    cd .. && npm install
    Build Command:      npm run build

  El vercel.json en la raíz ya indica:
    "framework": "nextjs"
    "rootDirectory": "frontend"

  Si usas Opción A, revisa que Build Command ejecute el script del monorepo
  que hace: npm run build --workspace=frontend

Paso 3 — Variables de entorno
-----------------------------
  Settings → Environment Variables

  Añadir las 3 variables para Production, Preview y Development:

    NEXT_PUBLIC_SUPABASE_URL
    NEXT_PUBLIC_SUPABASE_ANON_KEY
    SUPABASE_SERVICE_ROLE_KEY

  Valores: los mismos copiados de Supabase (sección 5, paso 4).

Paso 4 — Deploy
---------------
  1. Pulsar Deploy
  2. Si falla: revisar logs de build
  3. Error típico: @cg/backend no encontrado → corregir Install Command

Paso 5 — Probar en producción
-----------------------------
  1. Abrir URL de Vercel (ej: https://tu-app.vercel.app)
  2. Crear una sala
  3. Abrir la misma URL de sala en otro dispositivo o navegador
  4. Host: elegir juego e iniciar partida
  5. Hacer acciones → el otro cliente debe actualizarse
  6. Verificar en Supabase Table Editor que game_state cambia en rooms

    → backend/src/services/supabase.ts (lecturas/escrituras en API routes)

Sin Supabase configurado
------------------------
  El proyecto funciona en MEMORIA (globalThis.__cgRooms).
  Solo válido para desarrollo local en una misma instancia del servidor.
  En Vercel SIN Supabase: multijugador NO funciona entre usuarios reales.

9. ERRORES FRECUENTES Y SOLUCIONES
================================================================================

Problema: Las salas no se comparten entre usuarios en producción
Solución: Configurar las 3 variables de Supabase en Vercel. Sin ellas,
          cada instancia serverless usa memoria aislada.

Problema: Build falla — Cannot find module '@cg/backend'
Solución: Install Command desde raíz del monorepo:
          cd .. && npm install  (si Root Directory = frontend)
          o Root Directory = . con npm install en raíz.

Problema: Realtime no actualiza la UI
Solución: Verificar Replication en Supabase; confirmar NEXT_PUBLIC_SUPABASE_ANON_KEY
          en Vercel; revisar consola del browser por errores de canal.

Problema: Solo funciona en una pestaña / un usuario
Solución: Modo memoria activo → falta Supabase o SERVICE_ROLE_KEY incorrecta.

Problema: SERVICE_ROLE_KEY expuesta
Solución: Nunca en código cliente ni en repositorio. Solo env vars de servidor.

Problema: Error al ejecutar ALTER PUBLICATION en SQL
Solución: Activar Realtime manualmente en Database → Replication para
          rooms y room_players.

Problema: Acciones de juego lentas o duplicadas
Solución: Implementar withRoomLock y reducir polling redundante en useRoom.
